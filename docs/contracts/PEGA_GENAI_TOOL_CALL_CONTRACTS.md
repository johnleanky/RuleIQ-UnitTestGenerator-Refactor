# Pega GenAI Tool Call Contracts

- **Stage:** `S1 — Pega GenAI Tool Invocation Contracts`
- **Status:** `VERIFIED`
- **Scope:** Repository-only caller contract
- **External implementation owner:** User
- **Last updated:** 2026-09-03

## 1. Purpose and Boundary

This document defines how repository-designed GenAI agents call three externally implemented Pega tools:

- `WriteMemory(CaseID, Type, Payload)`
- `GetMemory(CaseID, Type, UUID)`
- `JsonValidationTool(CaseID, UUID, JsonSchema)`

It specifies caller ownership, parameter provenance, call order, minimum observable response fields, deterministic failure handling, UUID propagation, and static contract fixtures.

It does not design or create Pega Rule-AI-Tool rules, backing Activities or other backing rules, categories, rulesets, classes, storage, UUID generation, schema-engine logic, exports, ChangeRequests, deployments, or runtime tests. Those are user-owned under DEC-019.

The keywords MUST, MUST NOT, REQUIRED, and MAY are normative.

## 2. Fixed Cross-Tool Invariants

1. `CaseID` is the exact `pyID` obtained from `GetCaseData`, for example `GenUT-11007`. A caller MUST NOT add a workpool class, use `pzInsKey`, trim, normalize, or reconstruct it.
2. `RUTType` is captured once from the original `RuleJSON.pxObjClass` and remains unchanged across Generator and Validator calls. It is not a Memory-tool parameter.
3. The only valid Memory `Type` values are the case-sensitive literals `ScenarioGroup` and `UnitTestCandidate`.
4. `Payload` is opaque. Callers MUST NOT trim, parse, normalize line endings, decode entities, reformat JSON, or otherwise change it while transferring it through Memory.
5. `UUID` is generated by `WriteMemory` and is opaque. Callers MUST store and forward the exact returned string without construction, parsing, normalization, case conversion, validation against a locally invented pattern, or fallback substitution.
6. Every read is addressed by the exact `CaseID + Type + UUID` tuple. A caller MUST NOT request or accept a latest, first, most-recent, CaseID-only, or Type-only record.
7. Every successful `WriteMemory` call represents a new immutable record. A repair writes a new `UnitTestCandidate` and receives a new UUID; it never overwrites or reuses an earlier candidate UUID.
8. A `WriteMemory` call is single-attempt. No agent may automatically retry it unless a future accepted decision adds an idempotency contract.
9. Tool execution failure is distinct from a valid tool result that reports schema-invalid candidate content.
10. Static fixtures in this document prove caller behavior only. They do not prove external Pega runtime behavior.

## 3. Caller Ownership and Allowlist

| Caller | `WriteMemory` | `GetMemory` | `JsonValidationTool` | Agent handoff |
|---|---|---|---|---|
| Scenario Author | `ScenarioGroup` only | Forbidden | Forbidden | Calls `UnitTestGenerator(CaseID, RUTType, ScenarioGroupUUIDs)` once after every group write succeeds. |
| UnitTestGenerator | `UnitTestCandidate` only | `ScenarioGroup` only | Forbidden | Calls `UnitTestValidator(CaseID, RUTType, UnitTestCandidateUUID)` with the current candidate UUID. |
| UnitTestValidator | Forbidden | `UnitTestCandidate` only | Required before candidate read | Returns one `ValidatorReport`; it never mutates Memory. |

An agent MUST treat a tool outside its row as unavailable even if the Pega environment exposes it.

## 4. Parameter Provenance

| Value | Authoritative source | Consumers | Preservation rule |
|---|---|---|---|
| `CaseID` | `GetCaseData.pyID` | All three agents and all three tools | Pass unchanged for the full run. |
| `RUTType` | Original `RuleJSON.pxObjClass` | Generator and Validator agent handoffs | Capture once; never infer from candidate JSON or change during repair. |
| `ScenarioGroup` Payload | Final Scenario Author semantic audit for one physical unit-test group | Author write, Generator exact read | Serialize once before write; Memory transfer is opaque. |
| `ScenarioGroupUUIDs` | Ordered successful Author `WriteMemory` results | Generator handoff and ordered reads | Preserve array order and every UUID string exactly. |
| `UnitTestCandidate` Payload | Generator projection of the ordered groups | Generator write, Validator exact read | Write the complete current candidate; later repairs create new versions. |
| `UnitTestCandidateUUID` | Successful Generator `WriteMemory` result for the current version | Generator-to-Validator handoff; Validator schema and read calls | Replace the current variable only after a new write succeeds; forward unchanged to both Validator tool calls. |
| `JsonSchema` | Validator mapping from immutable `RUTType` | `JsonValidationTool` | `Rule-Obj-When` maps to `Rule-Test-Unit-Case_MultInpComb-JsonSchema`; all other supported RUT types map to `Rule-Test-Unit-Case_JsonSchema`. |

## 5. Common Observable Result Contract

The examples below use JSON only as a logical representation of named outputs. The external Pega implementation MAY include platform metadata, but the calling agent MUST be able to observe the required named fields with the exact casing and meanings defined here.

Every tool result has these common fields:

| Field | Type | Required | Meaning |
|---|---|---|---|
| `Success` | boolean | Yes | `true` means the tool invocation completed and tool-specific output fields are authoritative. `false` means tool execution failed. |
| `ErrorCode` | string | Yes | Empty when `Success=true`; one allowed tool-specific code when `Success=false`. |
| `ErrorMessage` | string | Yes | Empty when `Success=true`; non-empty diagnostic text when `Success=false`. Agents must not expose internal payloads or parameters from it. |

A result is malformed when any required field is absent, has the wrong type, uses an unknown error code, reports `Success=true` with non-empty error fields, reports `Success=false` with empty error fields, or violates a tool-specific field invariant.

A malformed result is handled exactly like tool execution failure. It MUST NOT be retried, repaired locally, or interpreted from generic prose. A response containing only a generic `response` field is malformed.

Error-code meanings are fixed at the caller boundary:

| Code | Meaning |
|---|---|
| `INVALID_INPUT` | A required parameter is absent or invalid before the requested operation can run. |
| `UNSUPPORTED_TYPE` | A Memory Type is not exactly `ScenarioGroup` or `UnitTestCandidate`. |
| `NOT_FOUND` | The supplied UUID does not identify any record. |
| `ADDRESS_MISMATCH` | The UUID identifies a record, but its CaseID or required Type does not match the supplied address. |
| `WRITE_FAILED` | A valid write request did not create a record. |
| `READ_FAILED` | A valid exact-read request could not complete because of an execution failure. |
| `VALIDATION_FAILED` | The exact candidate was resolved, but schema-engine execution did not complete; this is not schema-invalid content. |

## 6. `WriteMemory` Contract

### 6.1 Inputs

| Parameter | Type | Caller requirement |
|---|---|---|
| `CaseID` | string | Exact non-empty `GetCaseData.pyID`. |
| `Type` | string | Scenario Author uses only `ScenarioGroup`; Generator uses only `UnitTestCandidate`. |
| `Payload` | string | Complete caller-owned payload passed exactly as serialized, including boundary whitespace and line endings. |

The caller MUST perform its semantic or projection completion gate before calling. Memory is not asked to inspect Payload grammar or JSON validity.

### 6.2 Outputs

| Field | Type | Required | Invariant |
|---|---|---|---|
| `Success` | boolean | Yes | Common result semantics. |
| `UUID` | string | Yes | Non-empty only when `Success=true`; opaque and not locally validated. Empty when `Success=false`. |
| `ErrorCode` | string | Yes | Empty on success; otherwise `INVALID_INPUT`, `UNSUPPORTED_TYPE`, or `WRITE_FAILED`. |
| `ErrorMessage` | string | Yes | Common result semantics. |

Logical success example:

```json
{
  "Success": true,
  "UUID": "8f0d9bc1-6a20-4c5e-8a61-51b127f80ea2",
  "ErrorCode": "",
  "ErrorMessage": ""
}
```

Logical failure example:

```json
{
  "Success": false,
  "UUID": "",
  "ErrorCode": "WRITE_FAILED",
  "ErrorMessage": "The memory record was not created."
}
```

### 6.3 Caller Actions

- On a well-formed success, the caller records the returned UUID exactly once and continues.
- On failure or malformed response, the caller does not record a UUID, does not retry, and does not invoke any dependent agent or validation call.
- If Scenario Author has already written earlier groups and a later group write fails, it does not delete or overwrite earlier immutable records. It terminates the handoff and does not call Generator.
- If Generator candidate write fails, it retains the previous UUID only as history, does not present it as the current repaired version, does not call Validator, and returns `GeneratorRunReport.status=Failed`.

## 7. `GetMemory` Contract

### 7.1 Inputs

| Parameter | Type | Caller requirement |
|---|---|---|
| `CaseID` | string | Exact unchanged run CaseID. |
| `Type` | string | Generator uses only `ScenarioGroup`; Validator uses only `UnitTestCandidate`. |
| `UUID` | string | Exact opaque value returned by the corresponding successful write. |

### 7.2 Outputs

| Field | Type | Required | Invariant |
|---|---|---|---|
| `Success` | boolean | Yes | Common result semantics. |
| `Payload` | string | Yes | Exact stored string when `Success=true`; empty and non-authoritative when `Success=false`. A successful empty string is distinguishable by `Success=true`. |
| `ErrorCode` | string | Yes | Empty on success; otherwise `INVALID_INPUT`, `UNSUPPORTED_TYPE`, `NOT_FOUND`, `ADDRESS_MISMATCH`, or `READ_FAILED`. |
| `ErrorMessage` | string | Yes | Common result semantics. |

Logical success example:

```json
{
  "Success": true,
  "Payload": "SG|v=1\r\nS|id=S-1",
  "ErrorCode": "",
  "ErrorMessage": ""
}
```

Logical exact-address failure example:

```json
{
  "Success": false,
  "Payload": "",
  "ErrorCode": "NOT_FOUND",
  "ErrorMessage": "No record matched the exact address."
}
```

### 7.3 Caller Actions

- On success, the caller consumes Payload exactly as returned. Transport-layer normalization is forbidden.
- Generator MAY parse the returned `ScenarioGroup` according to the ScenarioGroup grammar because Generator owns that consumer contract; this does not permit Memory-layer parsing or transport mutation.
- Validator MAY parse the returned `UnitTestCandidate` only after schema validation for the same UUID succeeds.
- On failure or malformed response, the caller does not try another UUID, change CaseID or Type, request a latest record, or retry.
- A Generator group-read failure is terminal for that run because the ordered semantic input is incomplete; Generator MUST NOT silently omit the inaccessible group.
- A Validator candidate-read failure uses the exact ValidatorReport mapping in Section 7.4 and stops KnowledgeTool and semantic checks.

### 7.4 ValidatorReport Mapping for Candidate Read Failure

A failed or malformed Validator `GetMemory` result after successful schema validation MUST produce this report shape and fixed issue mapping:

```json
{
  "valid": false,
  "route": "HUMAN",
  "blocking": 1,
  "warnings": 0,
  "jsonSchemaValidation": {
    "isValid": true,
    "message": ""
  },
  "issues": [
    {
      "code": "MEMORY_READ_TOOL_ERROR",
      "severity": "B",
      "path": "/",
      "unit": null,
      "scenario": null,
      "decision": "",
      "action": "HUMAN_REVIEW",
      "message": "GetMemory could not return the exact candidate."
    }
  ]
}
```

The mapping is the same for `INVALID_INPUT`, `UNSUPPORTED_TYPE`, `NOT_FOUND`, `ADDRESS_MISMATCH`, `READ_FAILED`, and malformed `GetMemory` responses. `MEMORY_READ_TOOL_ERROR` is a required future Validator issue-code enum member, and `HUMAN_REVIEW` is its only action. S4 MUST add the new code and synchronize this code/action mapping across Validator prose, examples, and the closed report schema before implementing it in the Validator prompt/export.

## 8. `JsonValidationTool` Contract

### 8.1 Inputs

| Parameter | Type | Caller requirement |
|---|---|---|
| `CaseID` | string | Exact unchanged run CaseID. |
| `UUID` | string | Exact current `UnitTestCandidateUUID` supplied to Validator. |
| `JsonSchema` | string | Exact schema identifier derived from immutable input `RUTType`. |

The caller never supplies a Memory Type. The external tool contract fixes the resolved record type to `UnitTestCandidate`. The tool must validate the Payload at the exact CaseID and UUID, but its lookup and schema-engine implementation are external to this repository.

### 8.2 Outputs

| Field | Type | Required | Invariant |
|---|---|---|---|
| `Success` | boolean | Yes | Distinguishes tool execution from schema validity. |
| `IsValid` | boolean | Yes | Authoritative only when `Success=true`. `false` then means candidate content is schema-invalid, not that the tool failed. |
| `ValidationMessage` | string | Yes | Empty when `Success=true` and `IsValid=true`; non-empty schema diagnostics when `Success=true` and `IsValid=false`; empty and non-authoritative when `Success=false`. |
| `ErrorCode` | string | Yes | Empty on success; otherwise `INVALID_INPUT`, `NOT_FOUND`, `ADDRESS_MISMATCH`, `READ_FAILED`, or `VALIDATION_FAILED`. |
| `ErrorMessage` | string | Yes | Empty on success; non-empty tool-execution diagnostic on failure. |

Logical schema-valid result:

```json
{
  "Success": true,
  "IsValid": true,
  "ValidationMessage": "",
  "ErrorCode": "",
  "ErrorMessage": ""
}
```

Logical schema-invalid result:

```json
{
  "Success": true,
  "IsValid": false,
  "ValidationMessage": "/UnitTestRules/0: required property RuleCode is missing",
  "ErrorCode": "",
  "ErrorMessage": ""
}
```

Logical tool failure:

```json
{
  "Success": false,
  "IsValid": false,
  "ValidationMessage": "",
  "ErrorCode": "VALIDATION_FAILED",
  "ErrorMessage": "The schema engine did not complete."
}
```

### 8.3 Validator Actions

1. Validator validates `CaseID`, immutable `RUTType`, and current candidate UUID before any tool call.
2. Validator derives `JsonSchema` from immutable `RUTType` and calls `JsonValidationTool` exactly once.
3. If the result is failed or malformed, Validator does not call `GetMemory` or `KnowledgeTool`; it returns route `HUMAN` with issue code `JSON_VALIDATION_TOOL_ERROR` and action `HUMAN_REVIEW`.
4. If `Success=true` and `IsValid=false`, Validator classifies the schema diagnostics before returning `GENERATOR_REPAIR` and performs no `GetMemory` or `KnowledgeTool` call. For ordinary schema failure it copies the bounded `ValidationMessage` into `jsonSchemaValidation.message` and returns `JSON_SCHEMA_INVALID`. For 25 or more errors, broadly invalid root/UnitTestRules/Scenario/EvidenceSummary/RuleCode shape, or an oversized message, it MUST NOT copy the full diagnostics; it returns one compact `JSON_SCHEMA_MASS_FAILURE` issue with action `REBUILD_JSON_FROM_CURRENT_EVIDENCE`.
5. Only if `Success=true` and `IsValid=true` does Validator call `GetMemory(CaseID, UnitTestCandidate, UUID)` exactly once using the same CaseID and UUID. A failed or malformed result uses Section 7.4.
6. Validator has no tool retry loop and never calls `WriteMemory`.

## 9. Agent-to-Agent Call Contracts

### 9.1 Scenario Author to UnitTestGenerator

```text
UnitTestGenerator(
  CaseID=<exact GetCaseData.pyID>,
  RUTType=<immutable original RuleJSON.pxObjClass>,
  ScenarioGroupUUIDs=<ordered exact UUID array>
)
```

The call occurs exactly once after all physical ScenarioGroups pass semantic audit and every ordered `WriteMemory` succeeds. Scenario Author MUST NOT pass ScenarioGroup Payloads inline or invoke Generator with a partial UUID list after a write failure.

### 9.2 UnitTestGenerator to UnitTestValidator

```text
UnitTestValidator(
  CaseID=<exact run CaseID>,
  RUTType=<immutable original RUTType>,
  UnitTestCandidateUUID=<exact UUID of current candidate version>
)
```

The initial candidate produces the first UUID. Each projection repair produces a new candidate write and new current UUID before another Validator call. The maximum is the initial Validator report plus two repair attempts. Generator MUST NOT call Validator with an earlier UUID after a later write succeeds.

### 9.3 UnitTestGenerator Return to Scenario Author

S1 fixes only the return status and outer mapping; S3 defines the complete `GeneratorRunReport` shape.

| `GeneratorRunReport.status` | Scenario Author external result |
|---|---|
| `Completed` | `AIAgentResponseStatus=Completed` with empty error message. |
| `PartiallyCompleted` | `AIAgentResponseStatus=Completed` with empty error message. Partial details remain runtime-only and are not persisted or exposed by the outer response. |
| `Failed` | `AIAgentResponseStatus=Failed` with the bounded failure reason selected by the later S3/S5 contract. |

Scenario Author MUST NOT convert `PartiallyCompleted` into external `Failed`. Generator MUST NOT persist a separate partial-failure result record.

## 10. Deterministic Call Sequences

### 10.1 Nominal Flow

1. Scenario Author calls `WriteMemory(CaseID, ScenarioGroup, Payload)` once per physical group in deterministic order.
2. Scenario Author appends each successful UUID unchanged to `ScenarioGroupUUIDs`.
3. Scenario Author calls UnitTestGenerator once with CaseID, immutable RUTType, and the ordered UUID array.
4. Generator calls `GetMemory(CaseID, ScenarioGroup, UUID)` once for each UUID in array order.
5. Generator projects one combined candidate and calls `WriteMemory(CaseID, UnitTestCandidate, Payload)` once.
6. Generator calls Validator with the returned current candidate UUID.
7. Validator calls `JsonValidationTool(CaseID, UUID, JsonSchema)` once.
8. After schema success only, Validator calls `GetMemory(CaseID, UnitTestCandidate, UUID)` once with the same UUID.
9. Validator performs remaining read-only checks and returns `OK`.
10. Generator returns `Completed`; Scenario Author maps it to external `Completed`.

### 10.2 Projection Repair Flow

1. Steps 1–8 of the nominal flow use candidate UUID `candidate-v1`.
2. Validator returns `GENERATOR_REPAIR` for projection-only defects.
3. Generator repairs only allowed projection fields from unchanged ScenarioGroups.
4. Generator calls `WriteMemory` once and receives `candidate-v2`.
5. Generator replaces its current UUID with the exact returned `candidate-v2` string.
6. Generator calls Validator with `candidate-v2`; Validator uses `candidate-v2` for both schema validation and exact read.
7. `candidate-v1` remains immutable and is never overwritten or treated as current.
8. At most two repair writes and follow-up Validator calls occur after the first report.

### 10.3 Failure Short-Circuits

| Failure point | Required stop behavior |
|---|---|
| ScenarioGroup write | No retry; no Generator call; outer result is `Failed`. |
| ScenarioGroup exact read | No retry or fallback; no candidate write; Generator result is `Failed`. |
| Candidate write | No retry; no Validator call; Generator result is `Failed`. |
| JsonValidationTool execution/malformed result | No GetMemory or KnowledgeTool; Validator route is `HUMAN`. |
| Schema-invalid candidate | No GetMemory or KnowledgeTool; Validator route is `GENERATOR_REPAIR` using schema diagnostics. |
| Validator candidate exact read | No retry or fallback; no KnowledgeTool; Validator route is `HUMAN`. |
| Repair write | Keep earlier records immutable but do not reuse their UUID as the repaired current version; terminate `Failed`. |

## 11. Static Contract Fixtures

These fixtures are normative caller examples, not runtime test results.

### F01 — Opaque ScenarioGroup Round Trip

Input Payload, represented as a JSON string so boundary characters are visible:

```json
"  SG|v=1|name=A&B<\"Ω\">\r\nS|id=S-1|value=x|y  "
```

Expected calls and observations:

1. Author passes the exact decoded string to `WriteMemory` without trimming or entity encoding.
2. The successful returned UUID is stored unchanged.
3. Generator passes that exact UUID to `GetMemory`.
4. A successful read Payload must be code-point and line-ending identical to the input, including two leading spaces, two trailing spaces, `&`, `<`, quotes, `Ω`, `|`, and CRLF.

### F02 — Ordered Group Handoff

Given successful write UUIDs in physical-group order:

```json
["group-uuid-B", "group-uuid-A", "group-uuid-C"]
```

Generator receives and reads in exactly that order. Lexical sorting to A/B/C is forbidden.

### F03 — Cross-Case Isolation and No Fallback

Given a UUID returned for `CaseID=GenUT-100`, a read using `CaseID=GenUT-101` returns `Success=false` with `ADDRESS_MISMATCH`. The caller stops. It does not retry with `GenUT-100`, omit CaseID, or request the latest record.

### F04 — Cross-Type Isolation

Given a `ScenarioGroup` UUID, `GetMemory(CaseID, UnitTestCandidate, same UUID)` returns `Success=false` with `ADDRESS_MISMATCH`. Validator must not reinterpret or retry it as `ScenarioGroup`.

### F05 — Candidate Version Isolation

For the same CaseID and Type, candidate writes return `candidate-v1` and `candidate-v2`. Reads of v1 return only v1; reads of v2 return only v2. After v2 succeeds, Generator and Validator use only v2 as current while v1 remains unchanged.

### F06 — Schema-Valid Candidate

`JsonValidationTool` returns `Success=true`, `IsValid=true`, and empty messages. Validator then calls `GetMemory` once with the same CaseID and UUID and continues.

### F07 — Schema-Invalid Candidate

For an ordinary error set, `JsonValidationTool` returns `Success=true`, `IsValid=false`, and non-empty `ValidationMessage`; Validator returns one `JSON_SCHEMA_INVALID` repair result and performs zero GetMemory and KnowledgeTool calls. For 25 or more errors, broad structural failure, or oversized diagnostics, Validator does not copy the full message and returns one compact `JSON_SCHEMA_MASS_FAILURE` issue with action `REBUILD_JSON_FROM_CURRENT_EVIDENCE`.

### F08 — Schema Tool Failure

`JsonValidationTool` returns `Success=false` with `VALIDATION_FAILED`. Validator ignores `IsValid`, returns `HUMAN`, and performs zero GetMemory and KnowledgeTool calls.

### F09 — Malformed Tool Response

Any of these is malformed:

```json
{"response":"done"}
```

```json
{"Success":true,"UUID":"","ErrorCode":"","ErrorMessage":""}
```

```json
{"Success":false,"Payload":"","ErrorCode":"","ErrorMessage":""}
```

The caller treats the result as failure and does not infer missing data from prose.

### F10 — Write Failure and No Retry

A failed candidate write yields one invocation total, no usable UUID, zero Validator calls, and Generator status `Failed`. Reusing the prior candidate UUID to continue validation is forbidden.

### F11 — Unknown UUID

An exact read or schema validation with an unknown UUID returns `Success=false` with `NOT_FOUND`. The caller does not substitute another known UUID or a latest record.

### F12 — Immutable RUTType and Schema Choice

With original `RUTType=Rule-Obj-When`, every Validator invocation uses that unchanged value and every JsonValidationTool call uses `Rule-Test-Unit-Case_MultInpComb-JsonSchema`, even if a repaired candidate contains conflicting RUT metadata.

### F13 — Partial Generator Result Mapping

Given `GeneratorRunReport.status=PartiallyCompleted`, Scenario Author returns external `AIAgentResponseStatus=Completed` with an empty error message. It does not persist or expose partial-failure details and does not reinterpret the result as `Failed`.

## 12. Static Conformance Checklist

Repository prompt and agent-export work in S2–S5 must demonstrate all of the following:

- Every tool call uses the exact names and parameter names in this document.
- Every parameter is sourced according to Section 4.
- Every agent tool allowlist matches Section 3.
- UUID variables distinguish ordered ScenarioGroup UUIDs from the current UnitTestCandidate UUID.
- The same current candidate UUID reaches Validator, JsonValidationTool, and Validator GetMemory.
- No call path selects a latest or CaseID-only record.
- No write failure path retries or continues to a dependent call.
- JsonValidationTool failure and `IsValid=false` branch differently.
- Validator never writes Memory.
- Static fixtures cover all F01–F13 outcomes.
- No repository artifact claims external Pega runtime behavior was verified.

## 14. Verification Boundary

S1 repository verification may establish that this contract is complete, internally consistent, traceable, statically exercised, and correctly scoped. It may not establish that the user's Pega implementation conforms.

Future external conformance evidence may test persistence, immutability, exact isolation, UUID generation, schema execution, concurrency, importability, and platform-specific response serialization. Absence of that evidence does not block S1 repository closure and must remain explicitly unverified.
